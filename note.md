# Build a Pokajan-Inspired Card Game

Create a polished, fully playable **web-based recreation of the gameplay mechanics of “Pokajan!” from hololive Dreams**.

The objective is to reproduce the **game rules, flow, strategy, card interactions, scoring, and general table-game experience** as faithfully as possible while using **original placeholder artwork, fictional character names, and original UI assets**. Do not copy, extract, redistribute, or bundle proprietary hololive game assets, character artwork, audio, logos, fonts, or source code.

The resulting project should be sufficiently modular that custom character data and legally owned artwork can easily be substituted later.

## Recommended Technology

Use:

- React + TypeScript
- Vite or Next.js
- Tailwind CSS
- Framer Motion for animations
- Zustand or another lightweight state manager if useful
- No backend required for the initial implementation
- All game logic must run locally and deterministically
- Implement computer-controlled opponents
- Architect networking separately so multiplayer can be added later

If another stack is clearly better for the environment, use it, but maintain a clean separation between:

1. Game engine
2. Game state
3. AI players
4. UI
5. Card/character data
6. Animations/audio
7. Multiplayer interface

---

# 1. Core Concept

Pokajan is a four-player card game combining concepts reminiscent of poker and mahjong.

Four players compete for points.

Unlike mahjong or poker, successfully completing a hand **does not end the round**.

Instead:

1. The player declares **POKAJAN!**
2. The completed cards are removed from their hand.
3. Points are transferred.
4. Replacement cards are immediately drawn.
5. The same player may potentially complete another hand.
6. Normal play continues.

The game ends only when:

- a player's score reaches 0 or lower, or
- the draw pile is exhausted.

The player with the highest score wins.

# 5. The 100-Card Rule

This mechanic is important.

Even though the complete theoretical card pool generated by the four selected groups can contain **more than 100 cards**, only **100 cards are actually used during a match**.

Procedure:

1. Generate all theoretical cards belonging to the selected four groups.
2. Shuffle them.
3. Randomly retain exactly 100.
4. Cards excluded from those 100 are completely unavailable during the match.
5. Shuffle the resulting 100-card game pool.

Thus players can never know with absolute certainty whether the card they need actually exists in the current game.

From those 100 cards:

- Deal 7 cards to each player.
- 28 cards therefore enter starting hands.
- Remaining draw pile begins with **72 cards**.

Display:

```text
Deck: 72
```

and decrease it as cards are drawn.

# 8. Normal Turn Flow

Each player's normal turn follows this sequence:

### Step 1 — Draw

Automatically draw **1 card**.

A normal turn temporarily gives the player 8 cards.

Animate the drawn card separately before inserting it into the hand.

### Step 2 — Check Pokajan

Check whether one or more legal Pokajan combinations exist.

If one exists, enable a prominent:

# POKAJAN!

button.

Do **not** automatically activate the winning hand.

The player may intentionally decline a valid Pokajan to pursue a stronger hand.

### Step 3 — Optional Pokajan

If the player declares Pokajan:

- choose the valid combination if multiple hands exist
- calculate score
- transfer points
- remove participating cards
- draw replacement cards
- check again for another Pokajan

Multiple Pokajans may therefore occur consecutively.

### Step 4 — Discard

Eventually the active player must discard one card.

For the human:

- click card to select
- double-click, double-tap, or press a Confirm Discard button

Once discarded:

- card enters that player's public discard pile
- other players may potentially claim it
- if nobody does, turn moves clockwise

Discarding ends the player's normal turn.

# 13. Self-Draw Pokajan

When a player completes a Pokajan using their normal draw or cards already present during their turn, treat it as a **self-draw**.

The total hand value is paid collectively by the other three players.

Each opponent pays approximately one third.

Example:

```text
Pokajan value = 300
```

Each opponent pays:

```text
100
```

Winner receives:

```text
300
```

Implement integer-safe splitting.

If the score cannot divide perfectly by three, use a deterministic rounding policy and document it.

The total amount removed from opponents must equal the amount received by the winner.

Scores cannot become negative; clamp payments if necessary.

---

# 14. Discard Pokajan

A player may also complete a hand using another player's freshly discarded card.

This functions similarly to a Ron-style claim.

Example:

Player B discards:

```text
Mira Pink
```

Player D's hand contains:

```text
Mira Blue
Mira Orange
```

Player D can immediately declare:

# POKAJAN!

Player D completes the three-of-a-kind.

In this case:

**the discarding player pays the entire hand value.**

Example:

```text
Hand value = 120

Player B: -120
Player D: +120
```

The other two players pay nothing.

---

# 15. Discard Claim Window

Whenever a player discards a card:

1. Pause normal turn progression.
2. Check all other players for legal Pokajan combinations using that discard.
3. Give eligible human players a short decision window.
4. AI evaluates whether to claim.
5. Resolve winner.
6. Continue the match.

Visually display:

```text
POKAJAN AVAILABLE
[POKAJAN!] [PASS]
```

with a countdown.

Recommended decision timer:

**5–8 seconds**

Make it configurable.

---

# 16. Multiple Claims

If multiple players can claim the same discard:

1. Determine each claimant's resulting Pokajan score.
2. Highest-scoring Pokajan gets priority.
3. If multiple hands have the same value, give priority to the player closest to the discarder in normal turn order.

Only one discard claim should resolve.

Implement this as a dedicated resolver:

```ts
resolveDiscardClaims(discard, eligiblePlayers)
```

Do not let UI timing or race conditions determine the winner.

---

# 17. Replacement Draws After Pokajan

After declaring Pokajan:

1. Remove all cards forming the winning combination from the player's hand.
2. The triggering discard, if applicable, belongs to that completed combination.
3. Draw replacement cards until the player's normal hand size is restored.

The player effectively receives replacement draws corresponding to the cards consumed from their own hand.

For a typical:

- 3-card Pokajan → replenish the consumed hand cards
- 4-card group → replenish accordingly
- 5-card group → replenish accordingly

Model this carefully so hand size remains consistent with the original game's draw/claim flow.

After replacement cards are drawn:

**immediately check for another Pokajan.**

This allows:

```text
POKAJAN!
→ draw replacements
→ POKAJAN!
→ draw replacements
→ POKAJAN!
```

Implement visually satisfying chain indicators:

```text
POKAJAN!
CHAIN ×2
CHAIN ×3
```

---

# 18. The Game Does NOT Reset After Pokajan

This is one of the most important differences from poker/mahjong.

Do not:

- redeal hands
- reset discards
- reset scores
- start a new round

Instead the exact same game continues.

Completed sets simply leave the hand and new cards replace them.

---

# 19. Passing a Pokajan

A player is allowed to **decline** a valid Pokajan.

There should be no furiten-style penalty for doing so.

For example, a player could already possess:

```text
Aki Pink
Mira Pink
Luna Blue
```

which forms a mixed-color group.

They may choose **not** to declare it because they want:

```text
Luna Pink
```

to turn it into a same-color high-value group.

Passing should therefore remain a meaningful strategic option.

# 26. AI Opponents

Implement three competence levels:

### Easy

- prioritizes obvious completed hands
- discards mostly randomly
- always takes available Pokajan
- minimal card counting

### Normal

Evaluates:

- proximity to 3-of-a-kind
- proximity to group completion
- group size
- bonus cards
- same-color potential
- publicly visible cards
- dangerous discards
- current score
- cards remaining in deck

### Hard

Uses a weighted heuristic system.

Evaluate each possible discard using something similar to:

```text
Expected future hand value
+ completion probability
+ bonus-character potential
+ monochrome potential
+ replacement-draw value
- discard danger
- hand congestion
- deck exhaustion risk
- opponent comeback risk
```

Hard AI should alter its strategy based on position.

If leading:

- play defensively
- prefer safe discards
- accept smaller Pokajans
- accelerate deck depletion

If losing:

- tolerate more risk
- pursue 4/5-person groups
- pursue high-value monochrome hands
- avoid ending the game too quickly

AI must never inspect hidden cards belonging to other players.

Its decision making can only use information that a human player could legally know.

Be careful with duplicates.

Suppose the hand contains multiple possible representations of the same group:

```text

Mira Pink
Mira Orange

```

The engine must detect both:


and mixed alternatives.

Do not simply choose the first matching character instance.

Generate valid card combinations correctly.

```ts
  | "SELF_POKAJAN_DECISION"
```

Illegal actions must be impossible outside the relevant phase.

Example:

# 45. Validation Invariants

During development, assert these invariants:

```text
No physical card exists in two locations simultaneously.

Every active card is exactly one of:
- draw pile
- player hand
- discard
- completed Pokajan/meld

Initial active-card count = 100.

No player score < 0 after transaction settlement.

Only current player may normally draw/discard.

Only eligible opponents may claim a discard.

A Pokajan must correspond to a valid detected hand.

Hidden information must never influence non-cheating AI decisions.
```

In debug builds, throw errors when these invariants fail.

# 49. Quality Requirement

Do not provide merely a static mockup.

The final application must be an **actual functioning card game** with:

- correct deck construction
- correct hand detection
- turn management
- legal discards
- self-draw Pokajans
- discard Pokajans
- score transfers
- replacement draws
- chained wins
- AI opponents
- deck exhaustion
- end-game ranking

Prioritize gameplay fidelity, maintainability, and automated tests.

When there is uncertainty about a minor presentation detail from the original game, choose a sensible implementation rather than blocking development.

For uncertain **game-rule behavior**, isolate the behavior behind a configurable rule constant so it can easily be corrected after further verification.

Start by defining the complete TypeScript domain model and game-state machine, then implement and test the engine before building the interface.
